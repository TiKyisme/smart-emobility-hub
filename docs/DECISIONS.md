# Design Decisions

Record only decisions needed to resolve ambiguity. Do not use this file to invent new requirements.

| ID | Decision | Reason | Requirement impact |
|---|---|---|---|
| D-001 | The MVP uses simulated in-memory data and no backend database. | Explicitly permitted by assignment. | FR-19, NFR-04 |
| D-002 | The implementation uses a simple layered module organization in plain HTML/CSS/JavaScript. | Layered architecture is present in lecturer slides and supports a small demonstrable MVP without unnecessary infrastructure. | All |
| D-003 | The page uses a fixed `STUDENT-DEMO` identity for student actions; authentication and account management are not implemented. | Student workflows need an actor identifier for reservation ownership, while account management is explicitly out of scope. | FR-04..FR-09, NFR-04 |
| D-004 | Active parking reservations hold capacity separately from physical occupancy; both are included when deciding whether another space can be allocated or a Hub is at risk. | The specifications require capacity-safe reservation and return behavior but do not define whether reserved spaces are included in the occupancy field. This keeps the invariant explicit without changing simulated physical state. | FR-05, FR-07, FR-12, NFR-03 |
| D-005 | Manual simulated updates are immediate; optional automatic updates run every 15 seconds and show the latest simulator message in the UI. | NFR-01 leaves the maximum delay for team decision, and a short deterministic cadence makes near-real-time behavior demonstrable without external hardware. | FR-19, NFR-01 |
| D-006 | UI clarity is accepted when the main Student and Operator flows are available on one page, each action has visible success/failure feedback, and the resulting resource state is rendered immediately. | NFR-05 requires a measurable team criterion but does not supply one. | NFR-05, all workflows |
| D-007 | The shared-vehicle hold duration is configurable through `RESERVATION_HOLD_DURATION_MS`; the MVP default is 15 minutes. | The assignment requires expiry but does not specify an exact duration, so the value is an explicit team decision rather than a lecturer-provided threshold. | FR-04, NFR-02 |
| D-008 | A shared-vehicle charging request takes its battery level and upcoming-usage flag from the recorded vehicle state; only a private EV's battery level is entered by the student (0–100, validated). | The system already holds shared-vehicle battery data (FR-03, `Vehicle.getBatteryLevel()` in the class design). Typed values let the queue contradict the vehicle table and could distort priority. | FR-08, FR-09, FR-15 |
| D-009 | A queued shared-vehicle request receives a charging point only while its vehicle is available at the requested Hub. Otherwise it stays queued and is shown "on hold" with the reason (reserved, in use, failed, charging, moved). A vehicle can have at most one open (queued or scheduled) request. | Prevents charging capacity from being allocated to vehicles that cannot use it and prevents double allocation after incidents or reservations. | FR-08, FR-14, FR-15, NFR-03 |
| D-010 | Simulated parking arrivals follow D-004 (physical + held spaces). Simulated charging-point occupancy is temporary: the simulator releases the point it occupied on its next charging tick and never changes points used by scheduled or seeded charging sessions. | The simulator must not create states the live services would reject (over-capacity parking) or permanently consume charging capacity during a demo. | FR-19, NFR-03 |
| D-011 | Interface mode covers both Light/Dark and VI/EN language. Like the theme, the language choice is in-memory; a reload starts in English/Light. | Submission #2 records the lecturer's clarification that the mode controls are Light/Dark and VI/EN. Persistence is not required by the assignment. | FR-20 |
| D-012 | For a live demonstration the hold duration may be shortened through the page URL, e.g. `?holdSeconds=60` (accepted range 10–3600 s). The page always displays the active hold duration; without the parameter the default of D-007 applies. | Lets the expiry path of FR-04 be shown in class without waiting 15 minutes, without editing source code and without a hidden flag. | FR-04 |
| D-013 | The What-if result reports "live state unchanged" only after comparing a serialized snapshot of the live state taken before and after the run. | The UI claim is verified on every run instead of being a constant. | FR-16, FR-17 |
