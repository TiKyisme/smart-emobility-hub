# Design Decisions

Record only decisions needed to resolve ambiguity. Do not use this file to invent new requirements.

## Architectural decisions of the Submission #3 report

The Submission #3 report summarizes six architectural decisions (Table 2, "ADR-01..ADR-06"). They map to the decision records below.

| ADR (Submission #3) | Title | Decision records |
|---|---|---|
| ADR-01 | Client-side in-memory architecture for the MVP | D-001, D-002 |
| ADR-02 | Single-page application with user contexts | D-003, D-006 |
| ADR-03 | Reactive observer state store (`createStore`: getState, update, subscribe) | D-002 (`src/state/store.js`) |
| ADR-04 | Reservation hold window and expiry clean-up (15 minutes, `expireReservations`) | D-007, D-012 |
| ADR-05 | Smart charging priority: starting battery below 20 % or early departure | D-015, D-019 |
| ADR-06 | Isolated what-if space (deep-cloned snapshot) | D-013, D-024 |

## Decision records

| ID | Decision | Reason | Requirement impact |
|---|---|---|---|
| D-001 | The MVP uses simulated in-memory data and no backend database. | Explicitly permitted by assignment. | FR-19, NFR-04 |
| D-002 | The implementation uses a simple layered module organization in plain HTML/CSS/JavaScript. | Layered architecture is present in lecturer slides and supports a small demonstrable MVP without unnecessary infrastructure. | All |
| D-003 | Each actor of the use case diagram has one fixed demo identity: `STUDENT-DEMO`, `OPERATOR-DEMO`, `DISPATCH-DEMO` (Vehicle Dispatch Staff) and `MAINT-DEMO` (Maintenance Staff); authentication and account management are not implemented. | Workflows need an actor identifier for ownership and assignment, while account management is explicitly out of scope. | FR-04..FR-09, FR-13, FR-14, NFR-04 |
| D-004 | Active parking reservations hold capacity separately from physical occupancy; both are included when deciding whether another space can be allocated or a Hub is at risk. | The specifications require capacity-safe reservation and return behavior but do not define whether reserved spaces are included in the occupancy field. This keeps the invariant explicit without changing simulated physical state. | FR-05, FR-07, FR-12, NFR-03 |
| D-005 | Manual simulated updates are immediate; optional automatic updates run every 15 seconds and show the latest simulator message in the UI. | NFR-01 leaves the maximum delay for team decision, and a short deterministic cadence makes near-real-time behavior demonstrable without external hardware. | FR-19, NFR-01 |
| D-006 | UI clarity is accepted when every use case of the diagram has its own page in the sidebar, grouped by actor and named like the use case, each action has visible success/failure feedback, and the resulting resource state is rendered immediately. | NFR-05 requires a measurable team criterion but does not supply one; the pages follow the Submission #2 mockup navigation. | NFR-05, all workflows |
| D-007 | The shared-vehicle hold duration is configurable through `RESERVATION_HOLD_DURATION_MS`; the MVP default is 15 minutes. | The assignment requires expiry but does not specify an exact duration, so the value is an explicit team decision rather than a lecturer-provided threshold. | FR-04, NFR-02 |
| D-008 | A shared-vehicle charging request takes its battery level and upcoming-usage flag from the recorded vehicle state; only a private EV's battery level is entered by the student (0–100, validated). | The system already holds shared-vehicle battery data (`Vehicle.getBatteryLevel()` in the class design). Typed values let the queue contradict the vehicle table and could distort priority. | FR-08, FR-09, FR-15 |
| D-009 | A waiting shared-vehicle request receives a charging port only while its vehicle is available at the requested Hub. Otherwise it stays waiting and is shown "on hold" with the reason (reserved, in use, failed, being moved, moved). A vehicle can have at most one open request, and the operator form only offers eligible vehicles. | Prevents charging capacity from being allocated to vehicles that cannot use it and prevents double allocation after incidents or reservations. | FR-15, NFR-03 |
| D-010 | Simulated parking arrivals follow D-004 (physical + held spaces). Simulated port occupancy is temporary: the simulator releases the port it occupied on its next charging tick and never changes ports used by charging sessions. | The simulator must not create states the live services would reject (over-capacity parking) or permanently consume charging capacity during a demo. | FR-19, NFR-03 |
| D-011 | Interface mode covers both Light/Dark and VI/EN language. The page starts in Vietnamese/Light; like the theme, the language choice is in-memory. | Submission #2 records the lecturer's clarification that the mode controls are Light/Dark and VI/EN; the team presents in Vietnamese. Persistence is not required by the assignment. | FR-20 |
| D-012 | For a live demonstration the hold duration may be shortened through the page URL, e.g. `?holdSeconds=60` (accepted range 10–3600 s). The page always displays the active hold duration; without the parameter the default of D-007 applies. | Lets the expiry path of FR-04 be shown in class without waiting 15 minutes, without editing source code and without a hidden flag. | FR-04 |
| D-013 | The What-if result reports "live state unchanged" only after comparing a serialized snapshot of the live state taken before and after the run. | The UI claim is verified on every run instead of being a constant. | FR-16, FR-17 |
| D-014 | A student holds or uses at most one shared vehicle at a time. | Keeps the trip flow unambiguous and prevents one student from blocking several vehicles; the assignment does not ask for multiple simultaneous holds. | FR-04, FR-06, FR-07 |
| D-015 | Charging ports are allocated automatically: whenever a request becomes active or capacity/eligibility changes (session finished, port restored, vehicle repaired, hold expired or cancelled, simulator release), free ports go to the highest-priority eligible requests. Priority follows ADR-05 and FR-CHG-2: early departure or a battery below 20 % first, then the lower battery, then registration time. The operator can end a session early with "Finish": a shared vehicle is set to 100 % and becomes available. Sessions in progress are not pre-empted. | Submission #3 ADR-05 describes automatic priority scheduling; without session completion the charging capacity could only shrink. | FR-08, FR-09, FR-15, NFR-03 |
| D-016 | Incidents follow the Submission #2 lifecycle (D-021). Resolving an incident returns the resource to service: a repaired vehicle becomes available (one that failed during a trip or a redistribution needs a free space at its Hub), a restored port becomes available and is allocated immediately. | FR-14 requires handling incidents, not only recording them; a resource must be able to come back without reloading the page. | FR-14, FR-15 |
| D-017 | Students can cancel a vehicle hold before pickup, release a parking hold and cancel a booked or waiting charging session; the operator can cancel or move booked/waiting charging requests and cancel redistribution orders that have not started. Picking up a shared vehicle withdraws its charging request that has not started. | Completes the alternative flows (UC-04 A1, UC-09 A3, FR-OPT-17) and prevents stale holds from consuming capacity. | FR-04, FR-05, FR-08, FR-09, FR-13, FR-15 |
| D-018 | "Reset data" restores the seed data without reloading the page and keeps the chosen language and theme. | Makes repeated demo runs quick and predictable; it is the same as reloading the page, which also resets everything. | NFR-04 |
| D-019 | UC-09 charging is booked in one-hour time slots on clock hours, for today and tomorrow. A slot's capacity is the number of working ports of the Hub; a booking (status *Scheduled*) holds one port for its slot. When the slot starts the session waits for a port (*Waiting*) and is assigned by D-015 (*Charging*); it ends with the slot or when the operator presses *Finish*. A private EV's owner is notified when the session completes (FR-PEV-5). Shared vehicles are added by the operator to the earliest slot with a free port. Students book charging for private EVs only. | The Submission #2/#3 UC-09 design books a Hub and a time slot (mockup "20:00–21:00", `checkAvailability(hubId, slot)`, `TimeSlot`); Submission #1 assigns student charging requests to the Private EV Owner (FR-PEV-2) and the management of charging requests to smart charging (FR-CHG-1). Slot length and booking window are team decisions. | FR-08, FR-09, FR-15, NFR-03 |
| D-020 | A redistribution order moves one vehicle: on creation the vehicle becomes *Being moved* (not reservable) and one space is held at the destination; the Vehicle Dispatch Staff starts it (the vehicle leaves the source Hub) and completes it (vehicle and both Hubs updated, hold released). The operator can cancel an order that has not started. | Submission #1 FR-OPT-7..9 and FR-DIS-1..8 describe orders executed by the dispatch staff; holding the destination space keeps the return capacity-safe (D-004). | FR-13, NFR-03 |
| D-021 | Incident lifecycle: *New* (recorded) → confirm and classify (type, severity) → either *Assigned* to the Maintenance Staff (the resource is marked unavailable) → *In progress* → *Resolved*, or an operational action that restores the resource without repair → *Resolved*. "Confirm unavailable" takes the resource out of service at any time before resolution. One open incident per resource. | Follows the Submission #2 UC-15 activity diagram and mockup and the Submission #3 IncidentController / MaintenanceTask methods. | FR-14 |
| D-022 | UC-02 search: the student chooses a known place (a Hub or another campus place with simulated coordinates); Hubs within the radius (0.1–5.0 km, default 1 km) are listed nearest first using the Haversine distance; walking time assumes 80 m/min; data older than 5 minutes is flagged. The network has 12 Mobility Hubs. | Submission #1 leaves radius and battery threshold to the team and decides on 12 Hubs; Submission #3 specifies `validateLocation` (0.1–5.0 km) and Haversine; device GPS is out of scope. | FR-01..FR-03 |
| D-023 | Operator alert thresholds are configurable on the dashboard; defaults: overload at ≥ 85 % parking utilization (the threshold shown in the Submission #2 what-if mockup) and vehicle shortage below 1 available vehicle. | Submission #1 FR-OPT-4..6 require alerts "at the configured threshold" without giving numbers. | FR-12, FR-13 |
| D-024 | What-if model: the demand increase applies to the target Hub over the horizon (arrival surge: half of the extra riders need a space, half need a vehicle; full Hub: extra arrivals beyond capacity; charging surge: extra requests relative to current demand or port count; concentration: share of available vehicles moved in); offline ports are taken out at the target Hub. Labels: *critical* when parking ≥ the overload threshold, a vehicle shortage or a charging load above 100 %; *warning* from 70 % parking, below the shortage threshold or charging ≥ the overload threshold; *surplus* with ≥ 3 available vehicles and under 60 % parking. Runs are limited to 2 seconds. "Save scenario" keeps only the parameters; "Apply recommendations" creates redistribution orders and charging tasks in the live state only when the operator presses it. | The Submission #2 mockup and Submission #3 methods define the parameters, labels and actions, not the formulas; the values are team decisions. | FR-16..FR-18 |
| D-025 | The exception flows UC-04 E2/E3 and UC-09 E2 are demonstrated through the Data Simulator from a collapsed "Simulate an exception (demo)" section: the state of a vehicle or of a Hub's ports cannot be read for 10 seconds; another (simulated) student reserves the selected vehicle first. The normal services handle both. | In a single in-memory browser session these failures cannot occur on their own, but the reports specify and test them (TC-UC04-02, -06, -10). | FR-04, FR-09, FR-19 |
| D-026 | Vehicles have a type (E-Bike / E-Scooter) used by the search filter; the estimated range shown to students assumes 40 km (E-Bike) and 70 km (E-Scooter) on a full battery. | Submission #1 FR-SVU-1/2 search and display by vehicle type; the range estimate appears in the Submission #2 mockup. | FR-02, FR-03 |
